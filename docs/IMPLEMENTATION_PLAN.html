1. قرارات المشروع — بناءً على إجابات العميل

كل سطر هنا مربوط بإجابة مؤكدة من العميل — ليس افتراضاً.

السؤال
إجابة العميل
القرار التقني
التغطية الجغرافية
✓ المملكة كاملة
Google Maps يغطي كل المدن السعودية — دعم مسارات المسافات الطويلة بين المدن
GPS في الشاحنات
✓ موبايل السائق فقط
لا أجهزة GPS في الشاحنات — Flutter Geolocator يبث الموقع من هاتف السائق عبر Socket.io
نوع العملاء
✓ شركات فقط (B2B)
تسجيل الشركة: اسم + سجل تجاري + رقم ضريبي + جهة اتصال — فواتير ZATCA بصيغة B2B دائماً
تسعير الشحن
✓ يدوي من المشرف
العميل يُرسل الطلب بدون سعر → المشرف يراجع ويحدد السعر يدوياً → يُرسله بالإيميل للعميل → العميل يوافق أو يرفض — جدول التعريفة (pricing_tiers) يُستخدم كمرجع استرشادي للمشرف فقط
نظام قديم
✓ هنبدأ من صفر
لا data migration — لا scripts لاستيراد بيانات — فقط seed data أولية (مستخدمين + تعريفة + أنواع مركبات)
مستخدمين متزامنين
✓ 50–100 في الذروة
Railway Developer plan كافي — PostgreSQL instance واحد — Socket.io بدون clustering
ترقيم المركبات
✓ لوحة سعودية
المركبة تُعرَّف برقم اللوحة السعودية (3 أحرف + 4 أرقام) — validation في الـ API والـ Dashboard
من يدخل الطلبات
✓ الاثنين
العميل عبر التطبيق أو المشرف عبر الـ Dashboard نيابةً عنه — نفس الـ API، صلاحيات RBAC
أنواع الشحنات
✓ مبردة ومجمدة
ENUM: REFRIGERATED (2–8°C) أو FROZEN (أقل من -18°C) — المركبة تُصنَّف بقدرتها الحرارية — الإسناد يراعي التطابق
السائق يرفض الرحلة
✓ لا — إسناد مباشر
لا accept/reject في التطبيق — الرحلة تبدأ بحالة ASSIGNED — السائق يضغط "بدء الرحلة" مباشرة
متعدد المحطات
✓ نعم، مطلوب
جدول trip_stops — كل محطة: عنوان + جهة اتصال + وقت — السائق يوقّع ويصوّر في كل محطة — الرحلة تكتمل بعد كل المحطات
شروط الدفع
✓ مختلف حسب العميل
payment_terms_days في كل عميل — due_date في الفاتورة = تاريخ الإصدار + الأيام — تنبيه للمحاسب عند التأخر
