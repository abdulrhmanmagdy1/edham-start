## 1. نظرة عامة على المشروع

"إدهام" نظام لوجستي متكامل مصمم للسوق السعودي، يربط شركات العملاء (B2B حصراً) بأسطول مركبات متعدد الأنواع (Van + شاحنات مبردة + شاحنات ثقيلة) عبر تطبيق موبايل للسائقين وعملاء وواجهة ويب لغرف العمليات. يغطي النظام دورة الشحن كاملة: من إنشاء الطلب حتى التسليم والفوترة، مع دعم خاص لـ Cold Chain ومراقبة درجة الحرارة.

### 1.1 هدف النظام

**المشكلة:** تفتقر شركات اللوجستيات السعودية إلى نظام موحد يربط غرفة العمليات بالسائقين الميدانيين والعملاء في الوقت الفعلي، مما يؤدي إلى تنسيق يدوي عبر الهاتف والواتساب، وغياب تتبع الشحنات، وضعف رقابة Cold Chain.

**الحل:** منصة رقمية متكاملة تتيح:
- للعميل (الشركة): إنشاء طلبات الشحن وتتبعها لحظةً بلحظة
- للسائق: استلام مهامه ورفع تحديثات الرحلة من موبايله
- للمشرف: إدارة الأسطول وتخصيص الرحلات ومراقبة كل شيء من Dashboard مركزي
- للمحاسب: إصدار الفواتير وتتبع الإيرادات والمتأخرات
- للورشة: إدارة جدول الصيانة الدورية والأعطال

**نطاق الخدمة الجغرافي:** المملكة العربية السعودية كاملة، مع تركيز أولي على المدن الرئيسية: الرياض، جدة، الدمام، مكة المكرمة، المدينة المنورة، الخبر، أبها، تبوك، بريدة، الطائف.

### 1.2 نطاق MVP (الإصدار الأول)

- Mobile App (Flutter — Android + iOS): تطبيق موبايل بالـ 5 أدوار — عميل + سائق + مشرف + محاسب + ورشة
- Web Application (Next.js): موقع ويب كامل بالـ 5 أدوار — عميل + سائق + مشرف + محاسب + ورشة
- نفس الـ API ونفس اللوجين للمنصتين — المستخدم يدخل من أي منهما
- Backend API + PostgreSQL — دعم جميع الوظائف أعلاه
- Real-time Tracking — تتبع مواقع المركبات عبر GPS موبايل السائق
- Cold Chain Monitoring — تسجيل درجات الحرارة للشحنات المبردة والمجمدة
- نظام التسعير المختلط — تعريفة أساسية + تسعير خاص لكل شركة عميلة

### 1.3 ما خارج النطاق (v2+)

- إدارة الحاويات والموانئ (Container/Port Management) — [ASSUMPTION: مستقبلي رغم وجود صور ميناء، لأن التركيز الأساسي على عمليات بر الشحن]

## 2. أدوار المستخدمين

### 2.1 العميل (Customer) — شركات فقط (B2B حصراً)

- **الوصف:** شركة (مصنع، تاجر جملة، شركة توزيع، صيدليات، سلاسل بيع بالتجزئة) تستخدم إدهام لنقل بضاعتها داخل المملكة. النظام لا يدعم العملاء الأفراد — B2B حصراً. الشخص الذي يُسجّل الدخول هو ممثل الشركة (جهة الاتصال).
- **بيانات الشركة المطلوبة:**
  - اسم الشركة (company_name)
  - رقم السجل التجاري (commercial_registration_number)
  - الرقم الضريبي (vat_number) — لنظام ZATCA
  - اسم جهة الاتصال (contact_person_name)
  - رقم جوال جهة الاتصال (contact_phone)
  - البريد الإلكتروني للفوترة (billing_email)
  - شروط الدفع بالأيام (payment_terms_days) — يُحدده المشرف أو المحاسب
- **كيف يستخدم النظام:** يُنشئ طلبات شحن لحساب شركته، يتابع حالة شحنات الشركة، ويستلم الفواتير الضريبية B2B.
- **المصادقة:** [ASSUMPTION: رقم الجوال السعودي لجهة الاتصال + OTP — المعيار السائد في السوق السعودي]
- **الصلاحيات (يستطيع):**
  - إنشاء طلب شحن جديد لحساب شركته (من التطبيق)
  - تحديد نقطة الاستلام والمحطات المتعددة
  - اختيار نوع المركبة المطلوبة
  - تحديد نوع درجة الحرارة للشحنة (مبردة / مجمدة / جافة)
  - تتبع موقع شحنته في الوقت الفعلي
  - عرض تاريخ طلبات شركته
  - استلام وتنزيل الفواتير الضريبية
  - تقييم الخدمة بعد التسليم
  - التواصل مع المشرف عبر الإشعارات
- **الصلاحيات (لا يستطيع):**
  - الاطلاع على طلبات شركات أخرى
  - تعديل طلب بعد تخصيص سائق له
  - الوصول لمعلومات السائقين الشخصية (غير موقعه الحالي)
  - تعديل الأسعار أو الفواتير
  - تغيير بيانات الشركة المسجلة (يطلب ذلك من المشرف)
- **الشاشات (Flutter + Web):**
  - شاشة تسجيل الدخول / OTP
  - الرئيسية: قائمة الطلبات النشطة وآخر الطلبات
  - إنشاء طلب جديد (wizard متعدد الخطوات — يشمل تحديد المحطات المتعددة)
  - تفاصيل الطلب + خريطة تتبع حية + حالة كل محطة
  - سجل الطلبات السابقة
  - الفواتير والمدفوعات
  - الإعدادات والملف الشخصي (بيانات الشركة)
  - تقييم الخدمة (Post-delivery)

### 2.2 السائق (Driver)

- **الوصف:** موظف ميداني يقود إحدى مركبات إدهام وينفذ رحلات الشحن. يعمل في بيئة صحراوية وحضرية، وقد يفتقر للاتصال بالإنترنت في مناطق نائية.
- **كيف يستخدم النظام:** يستلم مهام الرحلة عبر الموبايل، يحدّث حالة الرحلة ومحطاتها، يرفع صور إثبات التسليم وتوقيع المستلم عند كل محطة.
- **المصادقة:** [ASSUMPTION: اسم المستخدم (رقم الموظف) + كلمة مرور — لأن السائقين موظفون لديهم حسابات إدارية يديرها المشرف، وليس تسجيل ذاتي]
- **الصلاحيات (يستطيع):**
  - استعراض الرحلات المُسندة إليه
  - تحديث حالة الرحلة (وصلت لنقطة التحميل / تم التحميل / في الطريق / وصلت للمحطة / تم التسليم في المحطة)
  - رفع صور إثبات التحميل والتسليم عند كل محطة
  - أخذ توقيع إلكتروني عند التسليم في كل محطة
  - الإبلاغ عن مشكلة أثناء الرحلة (عطل / حادث / إغلاق طريق)
  - عرض تفاصيل الشحنة (نوع البضاعة، متطلبات التبريد)
  - تسجيل قراءات درجة الحرارة للشحنات المبردة/المجمدة (يدوياً)
  - عرض سجل رحلاته السابقة
- **الصلاحيات (لا يستطيع):**
  - رفض الرحلة المُسندة إليه — الإسناد مباشر وإلزامي، لا يوجد زر قبول أو رفض
  - تعديل بيانات الطلب أو العميل
  - إسناد رحلات لسائقين آخرين
  - الوصول لبيانات مالية أو أسعار
  - رؤية طلبات غير مُسندة إليه
- **الشاشات (Flutter + Web):**
  - شاشة تسجيل الدخول (Employee ID + Password)
  - الرئيسية: الرحلة الحالية (بارزة) + الرحلات القادمة
  - تفاصيل الرحلة: خريطة + قائمة المحطات (Stops) بالترتيب + بيانات الشحنة
  - تحديث حالة الرحلة / المحطة الحالية
  - رفع صور التحميل / التسليم
  - شاشة التوقيع الإلكتروني (عند كل محطة)
  - مراقبة درجة الحرارة (للمبردات والمجمدات)
  - الإبلاغ عن مشكلة
  - سجل رحلاتي
  - الملف الشخصي

### 2.3 المشرف / Dispatcher (Supervisor)

- **الوصف:** موظف يجمع دور مدير العمليات والمسؤول الإداري — يدير العمليات اليومية للأسطول ويُدير حسابات الموظفين وصلاحياتهم.
- **كيف يستخدم النظام:** Web Dashboard على شاشات مكتبية Dell طوال يوم العمل.
- **المصادقة:** [ASSUMPTION: البريد الإلكتروني للموظف + كلمة مرور + 2FA اختياري — لأن المشرف لديه صلاحيات واسعة جداً]
- **الصلاحيات (يستطيع):**
  - عرض جميع الطلبات والرحلات
  - إنشاء وتعديل وإلغاء الطلبات نيابةً عن الشركة العميلة (عبر Dashboard)
  - إسناد رحلة لسائق ومركبة (إسناد مباشر بدون موافقة السائق)
  - تغيير إسناد الرحلة (إعادة تخصيص)
  - تتبع جميع المركبات على خريطة حية
  - مراقبة درجات حرارة الشحنات المبردة والمجمدة
  - إدارة ملفات السائقين (إضافة / تعطيل / تعديل)
  - إدارة المركبات (إضافة / تعطيل / جدولة صيانة)
  - إدارة ملفات العملاء (الشركات): إضافة / تعديل بيانات الشركة + شروط الدفع
  - عرض التقارير التشغيلية (KPIs)
  - إرسال إشعارات للسائقين والعملاء
  - قبول / رفض طلبات الصيانة من الورشة
  - عمليات جماعية (Bulk Operations): إسناد متعدد، تصدير بيانات
  - إنشاء وإدارة حسابات الموظفين (سائق / محاسب / ورشة / مشرف آخر)
  - تعيين الأدوار والصلاحيات لكل موظف
  - إدارة التعريفة الأساسية للأسعار (Base Pricing Tariff)
  - عرض سجلات النظام (Audit Log)
- **الصلاحيات (لا يستطيع):**
  - تعديل الفواتير المُصدَرة (صلاحية المحاسب)
  - حذف بيانات تاريخية
- **الشاشات (Flutter + Web):**
  - Dashboard الرئيسي (KPIs + خريطة حية + تنبيهات)
  - إدارة الطلبات (قائمة + فلترة + بحث + إنشاء نيابة عن الشركة)
  - تفاصيل الطلب + إسناد سائق + عرض المحطات
  - خريطة التتبع المباشر (Live Map)
  - إدارة الأسطول (Fleet Management)
  - تفاصيل المركبة (سجل الرحلات + الصيانة + Cold Chain)
  - إدارة السائقين
  - تفاصيل السائق (ملف + تقييمات + رحلاته)
  - إدارة العملاء (الشركات)
  - Cold Chain Monitor (شاشة مخصصة لدرجات الحرارة)
  - التقارير والإحصاءات
  - الإشعارات والتنبيهات
  - إدارة المستخدمين (إضافة موظفين / تعديل / تعطيل)

## 3. User Flows الرئيسية

### Flow 1: طلب رحلة جديدة من التطبيق (ممثل الشركة)

**الممثل:** ممثل شركة عميلة (B2B)
**المحفز:** الشركة تريد نقل بضاعة بمحطة واحدة أو أكثر
**المسبق:** الشركة مسجلة ومتحقق منها (رقم السجل التجاري + رقم ضريبي)

**Happy Path:**
1. ممثل الشركة يفتح التطبيق (سواء من تطبيق الموبايل أو الموقع) ويضغط "طلب شحن جديد"
2. يدخل عنوان نقطة الاستلام (مع دعم تحديد الموقع على الخريطة)
3. يُضيف المحطات (Stops) بالترتيب: عنوان كل محطة + اسم جهة الاتصال + رقم الهاتف + الوقت المجدول للوصول
4. يحدد نوع البضاعة وكميتها/وزنها
5. يحدد نوع درجة الحرارة: مبردة (2–8°C) / مجمدة (أقل من -18°C) / جافة
6. يختار نوع المركبة المطلوبة [ASSUMPTION: يُقترح النوع تلقائياً بناءً على الوزن ونوع الشحنة الحرارية، ويمكن تغييره]
7. يحدد تاريخ ووقت الاستلام المطلوب
8. يستعرض ملخص الطلب (المحطات والوزن والتواريخ فقط — بدون أي سعر). السعر يُحدَّد لاحقاً من المشرف بعد مراجعة الطلب
9. يضغط "إرسال طلب الشحن" (لا "تأكيد الطلب")
10. يصل إشعار للمشرف بطلب جديد
11. ممثل الشركة يرى حالة الطلب: "بانتظار التسعير" (PENDING_PRICING)
12. المشرف يستعرض الطلب ويُدخل السعر يدوياً في Dashboard
13. المشرف يضغط "تأكيد وإرسال السعر للعميل" → يُرسَل إيميل لبريد الفوترة
14. ممثل الشركة يرى السعر في التطبيق مع خيار: قبول → تُنفَّذ الشحنة / رفض → يُلغى الطلب
15. بعد قبول العميل → المشرف يُسند سائقاً ← هذا يحدث فقط بعد موافقة العميل
16. بعد إسناد المشرف لسائق، يتلقى ممثل الشركة إشعاراً بـ"تم تخصيص سائق"
17. ممثل الشركة يرى موقع المركبة على الخريطة وحالة كل محطة

**المسارات البديلة:**
- AP1: الشركة لديها عناوين محفوظة سابقاً → ممثلها يختارها من القائمة بدلاً من الكتابة
- AP2: الشركة لديها سعر خاص مخصص → يُطبَّق السعر التعاقدي تلقائياً دون تدخل
- AP3: إنشاء الطلب عبر المشرف نيابةً عن الشركة من Dashboard — يدخل Flow 1B
- AP4: ممثل الشركة يريد جدولة الطلب مسبقاً → يُحدد التاريخ والوقت المستقبلي

**حالات الخطأ:**
- لا توجد مركبات متاحة بالمواصفات المطلوبة (نوع الحرارة + الحمولة) → إشعار لممثل الشركة + إمكانية الانتظار أو تغيير الوقت
- ممثل الشركة يلغي الطلب بعد إسناد السائق → رسالة تأكيد + [ASSUMPTION: رسوم إلغاء تُحدد حسب سياسة الشركة]

### Flow 1B: إنشاء طلب من المشرف نيابةً عن الشركة العميلة

**الممثل:** مشرف في غرفة العمليات
**المحفز:** الشركة العميلة تتصل أو تُرسل طلباً خارج التطبيق (هاتف / واتساب)
**المسبق:** الشركة مسجلة مسبقاً في النظام

**Happy Path:**
1. المشرف يفتح Web Dashboard → إدارة الطلبات → "طلب جديد"
2. يختار الشركة العميلة من القائمة
3. يُدخل بيانات الطلب (المحطات، النوع، الوقت، نوع الشحنة الحرارية)
4. النظام يُطبق تلقائياً السعر الخاص بالشركة أو التعريفة الأساسية
5. يُؤكد الطلب
6. الطلب يدخل نفس دورة حياة الطلب العادي
7. يمكن للمشرف إسناد السائق فوراً من نفس الشاشة

---

### Flow 2: تخصيص سائق لرحلة (Supervisor)

**الممثل:** مشرف في غرفة العمليات
**المحفز:** ورود طلب شحن جديد (إشعار في Dashboard)
**المسبق:** يوجد سائقون ومركبات متاحة بالمواصفات المناسبة

**Happy Path:**
1. المشرف يرى إشعار "طلب جديد" في Dashboard
2. يفتح تفاصيل الطلب: المحطات، نوع البضاعة، نوع درجة الحرارة، الوقت المطلوب
3. ينظر لقائمة السائقين المتاحين مع مواقعهم الحالية على الخريطة
4. يختار أقرب سائق متاح بمركبة تدعم نوع الشحنة الحرارية المطلوبة
5. يضغط "إسناد للسائق"
6. يتلقى السائق إشعاراً: "تم إسناد رحلة جديدة إليك"
7. تُحدَّث حالة الطلب إلى "مُسند" وحالة الرحلة إلى ASSIGNED
8. يتلقى ممثل الشركة العميلة إشعاراً بتفاصيل السائق وموقع المركبة

**المسارات البديلة:**
- AP1: لا يوجد سائق متاح بمركبة مناسبة → المشرف يُحدد وقتاً لاحقاً للإسناد
- AP2: الطلب متعدد المحطات → يُسند كرحلة واحدة بقائمة المحطات

**حالات الخطأ:**
- المركبة خارج الخدمة (صيانة) → لا تظهر في قائمة المتاحة
- المركبة لا تدعم نوع الشحنة الحرارية المطلوبة → لا تظهر في قائمة المتاحة
- السائق انتهت صلاحية رخصة قيادته → تنبيه تلقائي ويُمنع الإسناد

---

### Flow 3: تنفيذ الرحلة (Driver)

**الممثل:** سائق
**المحفز:** استلام إشعار "تم إسناد رحلة جديدة إليك"
**المسبق:** السائق مسجل الدخول وتطبيقه نشط (GPS يبث موقعه عبر الموبايل)

**Happy Path:**
1. السائق يتلقى Push Notification: "تم إسناد رحلة جديدة إليك"
2. يفتح التطبيق ويرى تفاصيل الرحلة — قائمة المحطات بالترتيب — حالة الرحلة: ASSIGNED
3. لا يوجد زر قبول أو رفض — الإسناد مباشر
4. يبدأ التنقل لنقطة الاستلام
5. يصل لنقطة الاستلام → يضغط "وصلت لنقطة التحميل"
6. يُحمَّل البضاعة
7. يرفع صورة للبضاعة المحملة
8. إذا شحنة مبردة أو مجمدة: يُسجل قراءة درجة الحرارة الأولية
9. يضغط "تم التحميل — بدء الرحلة" → حالة الرحلة: IN_PROGRESS — يبدأ بث GPS
10. يتنقل للمحطة الأولى (مع تتبع GPS مستمر)
11. [اختياري] يُسجل قراءات درجة الحرارة دورياً أثناء الرحلة
12. يصل للمحطة الأولى → يضغط "وصلت للمحطة [1]" → حالة المحطة: IN_TRANSIT
13. يُسلَّم البضاعة للمستقبل في المحطة
14. يأخذ توقيع المستقبل الإلكتروني
15. يرفع صورة إثبات التسليم
16. يضغط "تم التسليم في المحطة 1" → حالة المحطة: DELIVERED
17. يكرر الخطوات 10–16 لكل محطة تالية
18. بعد اكتمال آخر محطة → حالة الرحلة: COMPLETED — يتوقف بث GPS
19. تُحدَّث حالة الطلب إلى "مكتمل"
20. يتلقى ممثل الشركة إشعار "تم تسليم جميع محطات شحنتك"

**المسارات البديلة:**
- AP1: لا يوجد أحد في نقطة تسليم محطة معينة → السائق يُبلغ المشرف وينتظر تعليمات
- AP2: الشحنة مبردة/مجمدة وتجاوزت درجة الحرارة الحد → تنبيه تلقائي للسائق والمشرف

**حالات الخطأ:**
- فقدان الاتصال بالإنترنت → الرحلة تستمر في الـ Offline Mode وتُزامَن عند عودة الإنترنت
- المستقبل يرفض البضاعة في محطة معينة → السائق يُبلغ المشرف ويُصور سبب الرفض
- تطبيق السائق يُغلق كلياً → يتوقف بث GPS وآخر موقع معروف يُعرض للمشرف مع تنبيه

---

### Flow 4: تتبع الشحنة (Customer)

**الممثل:** ممثل شركة عميلة
**المحفز:** يريد معرفة أين شحنته
**المسبق:** طلب موجود وسائق في الطريق

**Happy Path:**
1. ممثل الشركة يفتح التطبيق (سواء من تطبيق الموبايل أو الموقع)
2. يرى الطلب النشط في الرئيسية مع شريط التقدم وحالة كل محطة
3. يضغط على الطلب
4. يرى خريطة حية تُظهر موقع المركبة وخط سير الرحلة وجميع المحطات
5. يرى الوقت التقديري للوصول (ETA) للمحطة التالية
6. يرى سجل التحديثات (تم التحميل / وصل محطة 1 / في الطريق لمحطة 2 ...)
7. عند اكتمال جميع المحطات يتلقى إشعاراً "تم تسليم جميع محطات شحنتك"

**المسارات البديلة:**
- AP1: طلب بدون سائق مُسند بعد → يرى حالة "في انتظار التخصيص"
- AP2: ممثل الشركة لا يملك التطبيق → [ASSUMPTION: رابط تتبع عبر SMS/واتساب يُرسل تلقائياً عند بدء الرحلة]

**حالات الخطأ:**
- تطبيق السائق مغلق أو GPS متوقف → آخر موقع معروف يُعرض مع إشارة "آخر تحديث منذ X دقائق"

---

### Flow 5: إصدار فاتورة (Accountant)

**الممثل:** محاسب
**المحفز:** رحلة مكتملة تحتاج فوترة
**المسبق:** الرحلة في حالة "مكتمل"

**Happy Path:**
1. المحاسب يرى في Dashboard قائمة الرحلات المكتملة غير المفوترة
2. يختار رحلة → يستعرض تفاصيلها (مسافة / نوع مركبة / محطات / وقت)
3. يضغط "إنشاء فاتورة"
4. النظام يُحسب السعر تلقائياً: إذا للشركة سعر خاص → يُطبَّق، وإلا التعريفة الأساسية
5. يُضاف VAT 15% تلقائياً
6. يُحسب تاريخ الاستحقاق: تاريخ إصدار الفاتورة + payment_terms_days الخاص بالشركة
7. يُراجع المحاسب الفاتورة ويضغط "إرسال للعميل"
8. تُرسَل الفاتورة الضريبية B2B لبريد الفوترة (billing_email) وتظهر في تطبيق الشركة
9. يُسجل المحاسب الدفع عند استلامه

**المسارات البديلة:**
- AP1: فوترة متعددة (batch invoicing) لشركة لديها عدة طلبات → يختارها ويُنشئ فاتورة موحدة [ASSUMPTION]
- AP2: فاتورة تجاوزت due_date → تظهر في قائمة "المتأخرة" بلون مختلف في Dashboard المحاسب

**حالات الخطأ:**
- نقص في بيانات الشركة المالية (رقم ضريبي / billing_email) → تنبيه للمحاسب لتحديثها قبل الإرسال

---

### Flow 6: طلب صيانة مركبة (Workshop)

**الممثل:** موظف ورشة أو سائق أبلغ عن عطل
**المحفز:** عطل طارئ أبلغ عنه سائق، أو موعد فحص دوري قادم

**Happy Path (عطل طارئ):**
1. السائق يضغط "الإبلاغ عن مشكلة" في التطبيق
2. يختار نوع المشكلة (عطل ميكانيكي / إطار / تبريد / أخرى)
3. يُضيف وصفاً وصورة اختيارية
4. يصل البلاغ للمشرف وللورشة
5. موظف الورشة يُنشئ طلب صيانة في Dashboard
6. يُعيَّن الفني المسؤول ويُحدَّد الموعد
7. يُدخَل الفني التكلفة والإصلاحات بعد الانتهاء
8. يُحدَّث حالة المركبة: متاحة مجدداً
9. المشرف يتلقى إشعاراً بعودة المركبة للخدمة

**Happy Path (صيانة دورية):**
1. النظام يُذكّر تلقائياً قبل 7 أيام من موعد الصيانة الدورية
2. موظف الورشة يُنشئ طلب الصيانة الدورية
3. يُسجل المركبة "خارج الخدمة مؤقتاً"
4. ينفذ الصيانة ويُدخل التفاصيل
5. يُحدد موعد الصيانة الدورية التالي
6. يُعيد المركبة للخدمة

## 4. الميزات الأساسية (MVP)

### Feature 1: إدارة الطلبات (Order Management)

- **الوصف:** نظام كامل لدورة حياة طلب الشحن من الإنشاء حتى التسليم، يدعم محطات متعددة (Multi-Stop)، ويتيح الإنشاء من تطبيق الشركة أو Dashboard المشرف
- **User Stories:**
  - As a Customer (company rep), I want to create a multi-stop shipment order so that I can deliver goods to multiple locations in one trip.
  - As a Customer, I want to track my order and each stop's status in real-time so that I know where my goods are.
  - As a Supervisor, I want to create orders on behalf of client companies so that I can handle requests placed by phone.
  - As a Supervisor, I want to see all orders in one list with filtering options so that I can manage the workload.
  - As a Supervisor, I want to assign a driver directly to an order so that the shipment gets executed immediately.
- **معايير القبول:**
  - [ ] يمكن لممثل الشركة إنشاء طلب في أقل من 3 دقائق
  - [ ] يمكن للمشرف إنشاء طلب نيابةً عن الشركة من Dashboard بنفس بنية الطلب
  - [ ] الطلب يدعم محطة واحدة أو أكثر — كل طلب يحتوي مصفوفة stops[]
  - [ ] الطلب يمر بـ statuses: مسودة → بانتظار التسعير → تم التسعير → مؤكد من العميل → مُسند → جاري التحميل → في الطريق → مكتمل → مُلغى
  - [ ] الرحلة تمر بـ statuses: ASSIGNED → IN_PROGRESS → COMPLETED (لا يوجد PENDING_ACCEPTANCE)
  - [ ] كل محطة لها حالة مستقلة: PENDING → IN_TRANSIT → DELIVERED
  - [ ] الطلب لا يُعدّ مكتملاً إلا بعد تأكيد اكتمال جميع المحطات
  - [ ] كل محطة تتطلب: صورة إثبات تسليم + توقيع إلكتروني من المستلم
  - [ ] المشرف يستطيع رؤية جميع الطلبات مع فلترة بـ (الحالة / التاريخ / الشركة / السائق / نوع المركبة / نوع الشحنة الحرارية)
  - [ ] لا يمكن تعديل طلب بعد وصوله لحالة "في الطريق" إلا من المشرف
  - [ ] كل تغيير في حالة الطلب أو محطة يُولد إشعاراً للطرف المعني
  - [ ] لا يوجد زر قبول/رفض للسائق — الإسناد مباشر وإلزامي
  - [ ] السعر لا يُعرض للعميل عند إنشاء الطلب — المشرف هو الوحيد الذي يُحدد التكلفة
  - [ ] بعد تحديد المشرف للسعر، يُرسَل إيميل لبريد الشركة (billing_email) يحتوي السعر + زر قبول/رفض
  - [ ] العميل يستطيع قبول السعر → الطلب يتحول لـ CUSTOMER_CONFIRMED → يبدأ المشرف إسناد السائق
  - [ ] العميل يستطيع رفض السعر → الطلب يتحول لـ CANCELLED
- **حالات الحافة:**
  - طلب بأوزان تتجاوز حمولة المركبة المختارة
  - طلب مبرد يُسند لمركبة لا تدعم التبريد → يُمنع تلقائياً
  - طلب مجمد يُسند لمركبة تدعم التبريد فقط → يُمنع تلقائياً
  - إلغاء طلب بعد بدء الرحلة
  - محطة لا يصل إليها السائق (مغلقة / لا يوجد أحد)
- **قواعد العمل:**
  - الأسعار بالريال السعودي (SAR) حصراً
  - ضريبة القيمة المضافة 15% تُضاف تلقائياً لجميع الفواتير
  - حقل إلزامي في كل طلب: temperature_type (AMBIENT / REFRIGERATED / FROZEN)
  - المركبة المختارة يجب أن تتوافق مع temperature_type المطلوب
  - [ASSUMPTION: طلب الشحن يمكن جدولته مسبقاً بحد أقصى 7 أيام]

### Feature 2: إدارة الأسطول (Fleet Management)

- **الوصف:** إدارة المركبات بأنواعها الثلاثة مع تتبع حالتها وتاريخ صيانتها وقدراتها الحرارية
- **User Stories:**
  - As a Supervisor, I want to see all vehicles on a map so that I can dispatch the nearest available one.
  - As a Supervisor, I want to filter vehicles by temperature capability so that I match the right vehicle to cold chain orders.
  - As a Workshop employee, I want to mark a vehicle as out of service so that it's not assigned to trips.
- **معايير القبول:**
  - [ ] كل مركبة لها profile: رقم اللوحة السعودية + نوع المركبة + قدرة الشحن الحراري + السائق الافتراضي + حالة التشغيل + تاريخ آخر صيانة + موعد الصيانة القادمة
  - [ ] حالات المركبة: متاحة / في رحلة / في الصيانة / خارج الخدمة
  - [ ] كل مركبة تحمل حقل temperature_capability: NONE / REFRIGERATED_ONLY / FROZEN_ONLY / BOTH
  - [ ] عند إسناد رحلة: فلترة تلقائية للمركبات تضمن توافق temperature_capability مع temperature_type المطلوب
  - [ ] المشرف يستطيع عمل bulk operations (تصدير قائمة، تغيير حالة متعددة)
  - [ ] النظام يُنبّه تلقائياً عند اقتراب موعد الصيانة أو انتهاء رخصة المركبة
  - [ ] دعم 20+ مركبة في نفس الوقت بدون أداء منخفض
- **حالات الحافة:**
  - مركبة مبردة تعطل فيها نظام التبريد أثناء رحلة
  - سائق يُبلغ عن عطل وهو على بعد 200km من المدينة
- **قواعد العمل:**
  - رقم اللوحة السعودية = المعرّف الرئيسي للمركبة (Primary Identifier) — مثال: أ ب ج 1234
  - أنواع المركبات: `HIACE_VAN` / `ISUZU_REFRIGERATED` / `VOLVO_FH_HEAVY`
  - كل نوع له حمولة قصوى محددة (kg)
  - [ASSUMPTION: Toyota HiAce حمولة 1.5 طن / Isuzu 5 طن / Volvo FH 25 طن]

---

### Feature 3: التتبع في الوقت الفعلي (Real-time GPS Tracking)

- **الوصف:** تتبع مواقع جميع المركبات على خريطة حية عبر GPS موبايل السائق — لا يوجد جهاز GPS مثبت في الشاحنة
- **User Stories:**
  - As a Supervisor, I want to see all vehicles on a live map so that I can monitor operations.
  - As a Customer, I want to track my shipment's location so that I can plan for its arrival.
  - As a Driver, I want the app to record my location automatically so that the system knows where I am.
- **معايير القبول:**
  - [ ] GPS يعمل عبر Flutter Geolocator package على موبايل السائق
  - [ ] يُفعَّل GPS تلقائياً عند بدء الرحلة (IN_PROGRESS) ويُوقَف عند اكتمالها (COMPLETED)
  - [ ] تطبيق السائق يجب أن يكون نشطاً (foreground أو background service) لبث الموقع — إغلاق التطبيق كلياً يوقف البث
  - [ ] تحديث الموقع كل 30 ثانية أثناء الرحلة [ASSUMPTION: توازن بين الدقة واستهلاك بطارية الموبايل]
  - [ ] خريطة تعرض خط سير الرحلة المخطط والفعلي وجميع المحطات
  - [ ] ETA يُحسب ويُحدَّث تلقائياً لكل محطة
  - [ ] العميل يرى موقع سائقه فقط (وليس بقية الأسطول)
  - [ ] تُحفظ مسارات الرحلات لسجل تاريخي
  - [ ] في حال توقف بث GPS → آخر موقع معروف + timestamp + تنبيه للمشرف
- **قواعد العمل:**
  - دقة GPS تعتمد على جودة موبايل السائق وقوة إشارة الشبكة في المنطقة
  - [ASSUMPTION: Google Maps API للخرائط والمسافات — معيار السوق السعودي]
  - الخريطة تدعم RTL في الواجهة
  - [ASSUMPTION: تُحفظ بيانات GPS التاريخية لمدة 90 يوماً ثم تُحذف أو تُضغط]

### Feature 4: Cold Chain Monitoring (مراقبة سلسلة التبريد)

- **الوصف:** تتبع ومراقبة درجات الحرارة للشحنات المبردة والمجمدة طوال رحلتها، عبر إدخال يدوي من السائق في MVP
- **User Stories:**
  - As a Driver, I want to log temperature readings so that I comply with cold chain requirements.
  - As a Supervisor, I want to see temperature alerts so that I can intervene if cargo is at risk.
  - As a Customer, I want a temperature log report with my delivery so that I verify cold chain compliance.
- **معايير القبول:**
  - [ ] السائق يستطيع إدخال قراءة درجة الحرارة يدوياً في أي وقت أثناء الرحلة
  - [ ] نطاق درجة الحرارة المسموح يُضبط تلقائياً حسب temperature_type الطلب (لا يحتاج إدخال يدوي)
  - [ ] إذا تجاوزت القراءة الحد المسموح → تنبيه فوري للسائق والمشرف
  - [ ] تقرير Cold Chain يُولَّد تلقائياً مع كل شحنة مكتملة
  - [ ] في MVP: يعتمد على الإدخال اليدوي من السائق — التكامل مع أجهزة IoT في v2
- **قواعد العمل:**
  - مبردة (REFRIGERATED): 2°C إلى 8°C — للألبان والخضروات والأدوية
  - مجمدة (FROZEN): أقل من -18°C — للحوم والمأكولات البحرية والآيس كريم
  - المركبة يجب أن تحمل temperature_capability متوافقاً:
    - REFRIGERATED_ONLY أو BOTH → للشحنات المبردة
    - FROZEN_ONLY أو BOTH → للشحنات المجمدة

---

### Feature 5: نظام الإشعارات (Notifications)

## 5. متطلبات خاصة بالنظام

### 5.1 إدارة الأسطول (Fleet Management)

أسطول الشركة يضم 3 أنواع من المركبات:

| النوع | الرمز | الحجم | الاستخدام | قدرة الشحن الحراري الافتراضية |
|-------|-------|-------|-----------|-------------------------------|
| Toyota HiAce | `HIACE_VAN` | صغير | التوصيل الأخير (Last Mile) في المدن | NONE |
| Isuzu مبردة | `ISUZU_REFRIGERATED` | متوسط | الشحن المبرد/المجمد بين المدن والمستودعات | REFRIGERATED_ONLY / FROZEN_ONLY / BOTH (حسب تجهيز المركبة الفعلي) |
| Volvo FH | `VOLVO_FH_HEAVY` | كبير جداً | الشحنات الثقيلة والبضائع الضخمة | NONE / REFRIGERATED_ONLY / FROZEN_ONLY / BOTH (حسب تجهيز المركبة الفعلي) |

**ملاحظة:** temperature_capability يُحدد لكل مركبة بشكل منفرد عند تسجيلها في النظام — لا يُفترض تلقائياً من نوع المركبة.

**متطلبات الأسطول:**
- دعم 20+ مركبة بدون تدهور في أداء الخريطة الحية
- Bulk Operations: تصدير قائمة المركبات، تغيير حالة متعددة في خطوة واحدة
- رقم اللوحة السعودية = المعرّف الرئيسي للمركبة — مثال: أ ب ج 1234
- تاريخ كامل لكل مركبة: رحلاتها + صيانتها + سائقوها

### 5.2 Cold Chain Monitoring

**المتطلبات:**
- نوعان للشحن الحراري:
  - مبرد (Refrigerated): 2°C – 8°C — للألبان والخضروات والأدوية
  - مجمد (Frozen): أقل من -18°C — للحوم والمأكولات البحرية والآيس كريم
- شحنة جافة (Ambient/Dry): درجة حرارة الغرفة — لا رقابة حرارية
- آلية التسجيل في MVP: إدخال يدوي من السائق [ASSUMPTION: كل ساعتين كحد أقصى]
- في v2: تكامل مع أجهزة IoT لقراءة تلقائية
- تنبيه انتهاك: يُرسَل فوراً للسائق والمشرف عند الخروج عن النطاق
- تقرير سلسلة التبريد: يُولَّد مع كل شحنة مكتملة كـ PDF

### 5.3 التتبع في الوقت الفعلي (Real-time Tracking)

- GPS المصدر: Flutter Geolocator package على موبايل السائق — لا يوجد جهاز GPS مثبت في الشاحنة
- دقة GPS تعتمد على جودة موبايل السائق وقوة إشارة الشبكة في المنطقة
- التطبيق يجب أن يكون نشطاً (foreground أو background service) لبث الموقع — إغلاق التطبيق كلياً يوقف البث
- GPS يُفعَّل تلقائياً عند بدء الرحلة (IN_PROGRESS) ويُوقَف عند اكتمالها (COMPLETED)
- [ASSUMPTION: تُستخدم Google Maps Platform (Maps SDK + Directions API + Distance Matrix API)]
- تحديث الموقع: كل 30 ثانية أثناء الرحلة
- الخريطة تُظهر: موقع المركبة الحالي + جميع المحطات + خط السير
- للمشرف: جميع المركبات على خريطة واحدة مع ألوان حسب الحالة (متاح / في رحلة / في صيانة)
- [ASSUMPTION: تُحفظ بيانات GPS التاريخية لمدة 90 يوماً ثم تُحذف أو تُضغط]

### 5.4 العمل بدون إنترنت (Offline Mode)

مخصص للسائقين في المناطق الصحراوية النائية ذات تغطية شبكة ضعيفة:
- بيانات الرحلة الحالية (جميع المحطات وبياناتها) تُحمَّل مُسبقاً على الجهاز عند إسناد الرحلة
- تحديثات الحالة وقراءات الحرارة وصور التسليم تُخزَّن محلياً
- مزامنة تلقائية فور عودة الإنترنت بترتيب زمني
- المشرف يرى بجانب السائق مؤشر "غير متصل" مع آخر موقع معروف وتوقيته

## 6. الكيانات الرئيسية (Data Entities — ليست Schema)

فيما يلي قائمة بالكيانات الرئيسية في النظام مع أهم خصائصها. التصميم التفصيلي لقاعدة البيانات يُحدد في TECH.md.

- **User** — كل مستخدم في النظام: id / full_name / phone / email / role / status / created_at
- **Customer** — الشركة العميلة (B2B حصراً): id / company_name / commercial_registration_number / vat_number / contact_person_name / contact_phone / billing_email / payment_terms_days / billing_address / status / created_at
- **Driver** — السائق (يُوسّع User): employee_id / license_number / license_expiry / assigned_vehicle / status
- **Order** — طلب الشحن: id / customer_id / created_by (user_id — ممثل الشركة أو المشرف) / pickup_address / cargo_type / cargo_weight / vehicle_type_required / temperature_type (AMBIENT/REFRIGERATED/FROZEN) / scheduled_at / status / quoted_price (DECIMAL) / pricing_notes (TEXT) / pricing_sent_at (TIMESTAMP) / price_subtotal / price_vat / price_total / created_at
- **Stop** — محطة تسليم داخل الطلب: id / order_id / sequence_number / address / city / lat / lng / contact_name / contact_phone / scheduled_arrival / actual_arrival / status (PENDING/IN_TRANSIT/DELIVERED) / pod_photo / pod_signature
- **Trip** — الرحلة المنفذة: id / order_id / driver_id / vehicle_id / actual_start / actual_end / distance_km / status (ASSIGNED/IN_PROGRESS/COMPLETED) / created_at
- **Vehicle** — المركبة: id / plate_number (رقم اللوحة السعودية — Primary ID) / vehicle_type / make / model / year / capacity_kg / temperature_capability (NONE/REFRIGERATED_ONLY/FROZEN_ONLY/BOTH) / status / current_driver_id
- **TemperatureLog** — سجل درجات الحرارة: id / trip_id / recorded_at / temperature / recorded_by (driver_id) / is_violation
- **Invoice** — الفاتورة: id / order_id / customer_id / subtotal / vat_amount / total_amount / currency (SAR) / invoice_type (B2B_TAX) / status / issued_at / due_at (issued_at + payment_terms_days) / paid_at
- **PricingTariff** — التعريفة الأساسية: id / vehicle_type / temperature_type / price_per_km / min_price / effective_from / effective_to
- **ClientPricingOverride** — تسعير خاص بشركة عميلة: id / customer_id / vehicle_type / temperature_type / price_per_km / min_price / effective_from / effective_to
- **MaintenanceRequest** — طلب صيانة: id / vehicle_id / type (routine/emergency) / description / reported_by / assigned_to / cost / status / scheduled_at / completed_at
- **Notification** — الإشعار: id / user_id / type / title / body / is_read / created_at / reference_type / reference_id
- **AuditLog** — سجل التدقيق: id / user_id / action / entity_type / entity_id / changes / timestamp
- **Location** — بيانات GPS: id / vehicle_id / lat / lng / timestamp / accuracy / is_offline_synced
